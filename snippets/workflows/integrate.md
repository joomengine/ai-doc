# Import a snippet and verify a real consumer in Playground

## Inputs and test boundary

Use the [shared Playground workflow](../../testing/playground/README.md) by default for authorized implementation validation when browser access and a suitable target are available. Follow its [configuration reference](../../testing/playground/configuration.md) for environment setup, supported Joomla/PHP choices, installed JCB checks and browser/editor access. Honor the requested target or environment; if it is unavailable, record the blocker and unrun stages rather than silently substituting another version. Do not add a permission pause to testing already covered by the task.

Prepare the selected repository/read branch and exact commit, snippet/type GUIDs, compatible library definitions/assets, and a minimal Site View or Custom Admin View connected to a component with a reachable page. Record JCB, Joomla, PHP, template and UI-framework versions using the shared evidence format. Preserve existing local snippet, type, library and consumer edits before forced updates. This workflow is a procedure; execution is only claimed when [module verification](../verification.md) records it. A successful shared Power import is not evidence that these Snippet checks ran.

Run the static repository and creation-identity checks first. They do not execute or sanitize imported HTML, prove library resolution, or establish component behaviour.

## Repository acquisition and record round trip

1. **Configure the actual repository.** In JCB's repository configuration choose the **Snippet** content target (the inspected `RepoHelper` uses target `5`), an enabled/published record, correct host/organization/repository and read branch. For official core that means GitHub, `joomengine`, `snippets`, currently `master`. Legacy configuration defaults use a singular `snippet` repository under a configured Gitea organization; those defaults do not prove the official GitHub catalog is registered. Configure forks/custom catalogs explicitly. Record their ordering and verify the effective selected source for an overridden GUID using a distinctive expected value; do not infer precedence from a repository's name or a numeric ordering value alone. Check that the intended read branch is used rather than the write branch or the host's default branch.
2. **Verify access and discovery.** Open Snippets and use its Init toolbar operation (`snippets.initPowers`). The current controller opens `initialization_selection&power=Snippet&target=Snippets`. Confirm the intended repository and snippet identity appear, including the right title and description. An HTTP success or available repository row does not prove the selected item fetched correctly.
3. **Initialize deliberately.** Select the intended snippet and initialize it from the intended repository. Record whether each requested item was added, already local or not found; a success notification does not establish that every selected record was added. Base Init normally preserves an existing local GUID; it does not promise refresh. Verify the resulting item GUID, type/library GUIDs, decoded source, usage and attribution in the editor. Save and reopen to confirm the actual persisted values, not merely the listing or preview.
4. **Verify dependencies independently.** Confirm the referenced Snippet Type and Library exist with matching GUIDs and intended semantics. The package builder propagates an explicitly selected repository into recursive initialization; a snippet-only repository may not contain the external library package. Do not assume automatic fallback supplied it. Acquire/verify the proper library through its available package/Library flow or established local record, and inspect operation diagnostics. The fixture's local type is present; its Bootstrap v4 library remains external.
5. **Exercise refresh and reset separately.** Use the same snippet GUID and a controlled, distinctive source change on the test read branch. Capture the local record before each operation, exercise the applicable cases below, and compare the persisted source and relationships afterwards. When changing type or library references, verify the new target independently. A snippet Reset does not refresh the whole outgoing dependency graph.
6. **Test an export only when authorized.** Configure a test write branch/repository and use Push (`snippets.pushPowers`) if the task includes that write. Inspect emitted `item.json`, both applicable indexes, dependency rows and README. Confirm raw source remained raw, GUIDs stayed stable, optional clearing behaved as intended, and no local IDs/permissions/credentials leaked. A read-only test can compare the local record without publishing; record the export check as unexecuted in that case.

| --- | --- | --- |
| Init: `snippets.initPowers` | Opens repository/item selection; initializes selected identities with the selected repository. The selection table prevents selecting an already-local row; the underlying non-forced initializer also preserves existing local records. | A missing snippet is added. Reinspect these paths if the installed JCB version differs; similar toolbar labels do not establish identical behaviour.

## Copy, adapt, compile and render

7. **Select the consumer and libraries.** In the test Site View or Custom Admin View, select the expected library in the consumer's separate `libraries` control. The catalog snippet's `library` classifies the pattern; it does not automatically configure the view's assets. Verify real library version, CSS/JS paths, load order and conditions in the target build. Avoid loading an incompatible second Bootstrap or UIkit version just to make an old pattern appear styled.
8. **Inspect and copy source.** Choose the snippet to view its details, then copy/adapt its code into the consumer's actual HTML/default editor. The selector displays a textarea/usage; it does not write that code field automatically. Record every adaptation: translations, values/variables, output escaping, framework options, form actions, element IDs and required initialization.
9. **Save and test the copy boundary.** Confirm the source persists in the actual consumer field. The model clears the temporary `snippet` selection on save; this is expected. Reopening a view without the original selection does not mean its copied source was lost. With that saved copy in place, refresh a controlled catalog change using the appropriate operation above. Reopen the consumer and compare its saved source: it must remain unchanged until explicitly adapted. Then apply the intended update to the consumer blueprint and save. Record both comparisons so the test establishes that catalog selection is not a live binding.
10. **Compile and inspect the real consumer.** Compile the component that actually includes this view. Locate its generated template/layout and inspect the copied/adapted source and asset inclusion, using JoomEngine Code as described in the shared guide. Confirm the expected source change appears and there are no unresolved JCB placeholders, missing PHP variables/classes, invalid markup or duplicate identifiers. The consumer context controls placeholder expansion and PHP availability; a snippet catalog alone does not provide that context. An unrelated successful compilation does not cover the snippet.
11. **Install and verify browser behaviour.** Install the compiled test package into the intended Playground Joomla target and open the actual Site View route or Custom Admin View with the appropriate test permissions. Check relevant sizes, CSS/JS requests and response contents, console errors, labels, headings, keyboard navigation, focus handling, accessible state announcements where relevant, and interactions. Test empty/long/translatable content and repeated instances. Exercise dynamic values with benign HTML/attribute delimiters and confirm context-correct escaping in the rendered DOM; test URL restrictions, authorization, validation and CSRF cases where the adapted consumer uses them. A purely static panel does not require JavaScript interaction or form tests, but still needs semantic and layout inspection. Mark inapplicable cases with a reason instead of claiming them as passed.
12. **Record the outcome.** Use the [shared verification format](../../testing/playground/verification.md) and update the [module record](../verification.md) with source commits, effective repository/read branch, imported GUIDs, consumer/build identity, generated paths, checks run, observed results and unresolved gaps. Distinguish static format checks, JCB import/export, copy/update persistence, compilation and installed runtime/accessibility. Record failed, blocked and not-run stages explicitly. Do not call a snippet production-ready solely because its JSON parsed or its preview appeared.

## Security and accessibility are consumer responsibilities too

The current preview injects returned metadata and source into HTML; it is not a safe sandbox for arbitrary repository content. Review unfamiliar JSON/source as text before rendering. Do not assume `heading`, `usage`, description or links have been harmlessly escaped by every path.

When adapting dynamic output, escape for the actual HTML text, attribute, URL, JavaScript or CSS context. Do not insert raw user input into script/event handlers. PHP examples must declare their expected variables/services and respect the supported target APIs. A snippet containing a form needs the consuming component's routing, server-side authorization, validation and CSRF handling; visual markup does not provide those controls.

Use semantic elements, visible labels, suitable heading order and unique IDs. Interactive widgets need keyboard access, focus behaviour and accurate accessible state, not only ARIA attributes copied from an old example. State what still depends on the framework and target page. Localize end-user text through the consumer's normal language system, preserve placeholders accurately, and test translations that change text length.

Retain original code/license attribution and assess included external images/scripts separately. A contributor URL is not a license. Do not silently download or execute dependencies during a documentation check.

## Failure and recovery

If acquisition fails, retain exact source/ref/GUID and importer diagnostics; check paths, identity, enabled state, permissions, repository ordering/read branch and dependency availability. If rendering fails, inspect the saved consumer source, generated/installed view and actual asset requests before changing catalog identities. JoomEngine Code is useful for diagnosis, but an edit to installed PHP/HTML alone is not a maintained fix: return it to `item.json.snippet` when the reusable pattern is wrong, to the consuming JCB view/blueprint when adaptation is wrong, or to the responsible compiler source when generation is wrong. Repeat the applicable import/copy, compile, install and runtime checks from that authoritative source. If a regression affects already copied markup, include a migration note and test that consumer change independently.

Restore deliberate test changes through their known source/local revisions; do not indiscriminately reset unrelated local work. For a reproducible JCB defect, retain a minimal sanitized case and follow the shared [human issue-reporting procedure](../../testing/reporting-issues.md).
