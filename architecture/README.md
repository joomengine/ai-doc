# Architecture reference and task routing

This directory connects operational tasks in `skills` to the broader [Joomla Component Builder: Contextual Compilation Architecture](https://architecture.joomlacomponentbuilder.com/) publication. It is a source map, not a replacement edition of the white paper. JCB includes structured definitions, repository exchange, compilation, generated applications, recovery, and regeneration. Super Powers is one part of that lifecycle.

**Verified publication:** edition 1.0.0, 16 September 2026; repository revision [`7ac0ba83361e4b1d5181d2a441989ab17d50d63f`](https://github.com/joomengine/architecture/tree/7ac0ba83361e4b1d5181d2a441989ab17d50d63f), inspected 31 October 2026. The live article manifest reported the same source revision and 62 articles. Publication edition numbers are not JCB or Joomla software versions.

## Select the smallest sufficient reading path

Start with the relevant operational module and workflow. Read the architecture articles needed to understand a dependency, boundary, or failure. Do not require every agent to ingest the complete publication for a small change.

For implementation validation, follow the [shared Playground workflow](../testing/playground/README.md) and the module's `test_workflow` in the [registry](../registries/modules.json). Trace the authored definition through the local JCB record, an actual consuming blueprint, generated extension files and exercised runtime behaviour. Playground provides the default browser environment; each module defines its own assertions. A successful import or unrelated compilation does not establish the complete architectural path.

For concrete blueprint authoring, use the [Packages skill](../packages/SKILL.md), [sub-model router](../packages/models/README.md) and [field contract inventory](../packages/model-contracts.json). They connect the architecture to actual package records and nested settings, with separate routes to Field Types, Powers and Snippets when a dependency crosses model boundaries.

## Authority boundaries

1. **Project policy** states the desired maintenance approach, including Joomla-first reuse and the shared `joomengine/super-powers` foundation. Policy does not prove that the current implementation behaves correctly.
2. **The architecture publication** explains mechanisms and relationships. Its edition records the source captures behind those explanations. In this edition the core compiler study uses `bca4a1520484f3e2c2fbd12964a5995b0d058de1`, with separately fingerprinted integrated extrusion work. Do not label all of it as verified at today's branch tip.
3. **The implementation at the target revision** determines the operational contract. [Super Powers sources](../super-powers/sources.md), [Field Types sources](../field-types/sources.md), and [Snippets sources](../snippets/sources.md) record each module's separately inspected implementation and repository specimens.
4. **A project-specific plan** can restrict its own Joomla target, branches, or deployment scope. Such restrictions do not become ecosystem-wide rules. In particular, a Joomla 6-only blueprint-authoring MCP plan does not make every Super Power Joomla 6-only.

Super Powers contain reusable class definitions. Joomla Powers contain platform-reference mappings. Field Type catalogues define reusable field metadata and property choices. Snippet catalogues hold reusable content and classifications. Blueprint/package repositories serialize other JCB entities and relationships. They can refer to one another, but their indexes, payloads, and consumers must be documented independently.

## Adding the next operational module

Follow [the module authoring standard](../standards/module-authoring.md). Select the architecture articles relevant to the new module, inspect its real handlers and specimens, and author its own contract and workflows. Do not duplicate the entire architecture publication or mechanically rename the Super Powers files. Add the new module to the root routing and module registry only with an accurate coverage status. This architecture map is a reference bridge; it does not claim that every topic above already has a complete operational module in `skills`.

## Updating this map

Refresh the live article manifest and architecture repository together when links or edition claims change. Record the new exact revision, review relevant article differences, and keep historical pins where they are still the evidence for a historical claim. If a newer implementation conflicts with an older explanation, report the difference and update the affected operational contract from source; do not silently invent a reconciliation.
