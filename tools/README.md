# Verification tools

These tools enforce this repository's **portable authoring profile** and expose gaps; they do not implement the JCB compiler. Run them from an `ai-doc` checkout. They only read Power repositories. Fetching writes a new catalogue directory; GUID generation prints a candidate without reserving it.

## Requirements

- Bash 4+, `jq` 1.6+, Git, and GNU coreutils (`realpath`, `sha256sum`, `date`, `mktemp`, `sort`), `find`, `grep` and `sed`.
- PHP CLI (7.4+) with its tokenizer extension for syntax, declaration/body checks and the executable example. Missing PHP is reported as skipped checks. Choose the PHP versions actually supported by the consuming project; one successful PHP version does not prove the others.
- Linux's `/proc/sys/kernel/random/uuid`, or OpenSSL as the fallback secure random source.
- Network access to public GitHub repositories only for catalogue fetching. The regression suite is offline. ShellCheck is a separate CI check.

On Ubuntu, the required optional validation packages can be installed with `sudo apt-get install jq php-cli shellcheck`. Tools invoke `php -n`, which bypasses user PHP configuration, and explicitly load the tokenizer extension if needed. A nonstandard isolated PHP runtime can supply `PHP_TOKENIZER_EXTENSION` as the absolute path to its tokenizer shared library. No generated Power code is executed during repository validation. The separate example smoke test intentionally executes the small maintained example.

All public tools support `--help`.

## Fetch a current catalogue

```bash
bash tools/fetch-power-catalog.sh /tmp/jcb-power-catalog
```

The destination must not already exist. The optional second argument is a registry in the format of [power-repositories.json](../registries/power-repositories.json); extend it with authorized task-specific Power repositories before fetching. The current fetcher supports public GitHub repositories with HTTPS URLs, one branch per repository, and `super-powers.json`. Other Git hosts/private catalogues require an explicit, separately verified retrieval path; this tool does not pretend to support them.

For each registry entry, the tool fetches that branch once, reads its index from the fetched commit without checking out or executing repository code, and records:

| Output | Meaning |
| --- | --- |
| `manifest.json` | UTC retrieval timestamp, registry SHA-256, ordered repository IDs, URLs, branches, full commit SHAs, index paths and content hashes |
| `indexes/N.json` | Exact index bytes at that repository revision |
| `entries.json` | One record per GUID occurrence, retaining repository, revision and registry order |
| `shadowing.json` | Repeated GUIDs with first occurrence selected and later occurrences retained |

If any fetch or index validation fails, no completed output catalogue is published. Retry into a new directory after addressing access or source problems. A hash detects local accidental modification; it is **not** a signature or a guarantee that a manually edited manifest is trustworthy. Keep the catalogue generated by the fetcher and record its provenance.

Order is significant. Registry order is a discovery/validation input; configure the actual JCB consumer's repository order explicitly. Fetching never changes JCB configuration. A duplicate GUID may be an intentional overlay; review provenance and shadowed definitions instead of silently overwriting them in one dictionary.

## Generate a new identity

```bash
bash tools/new-power-guid.sh /tmp/jcb-power-catalog /path/to/working-power-repository
```

The additional local repository arguments are optional and repeatable. Supply every working repository containing unpublished powers. Each must have a valid `super-powers.json`; initialize an empty repository with `{}` before using it.

The tool requires a live catalogue containing **all seven official repository IDs**, verifies every index's hash and structure, rejects a future timestamp or age greater than 24 hours, generates a cryptographically random UUIDv4, and checks that candidate against every catalogue index and supplied local index. It prints only the UUID on success.

The 24-hour threshold is this tool's conservative operational policy, not a JCB requirement. Fetch again just before final publication, especially if work spans multiple sessions. Check any additional private/organization catalogues too. No distributed registry reservation occurs, and no tool can promise uniqueness across unknown repositories. Existing Powers retain their identities.

## Validate a working Power repository

```bash
bash tools/validate-power-repository.sh /path/to/working-power-repository /tmp/jcb-power-catalog
```

| Exit | Meaning and action |
| --- | --- |
| `0` | The implemented static checks passed; complete the relevant JCB integration and runtime checks |
| `1` | Malformed metadata, unsafe/missing paths, representation mismatch, invalid profile or PHP syntax failure; inspect the stated finding |
| `2` | One or more GUID references are absent from this catalogue; locate authorized additional sources or correct the reference, then rerun |

The validator checks:

- Canonical index shape, directory paths, GUID equality, and `Super---...---Power` index SPKs.
- Each indexed source file exists and resolves within the repository; path traversal and escaping symlinks are rejected. Unindexed `settings.json` files beneath `src` fail.
- Settings identities/types match the index; selector rows, PHP aliases, sentinels/custom names, flags, required version text and nested Composer rows follow the documented profile. Namespace segments are valid identifiers or placeholders, contain at least two backslash-separated parts, and the final dot/backslash segment matches `name`. Composer autoloader paths must be relative POSIX paths without traversal.
- PHP's non-executing tokenizer identifies the actual namespace and exactly one named declaration, ignoring comments and strings; its class/interface/trait name and type must match the metadata. PHP lint additionally checks syntax.
- Ordinary `code.power` is parsed inside a synthetic declaration and must equal the extracted generated declaration body after CRLF and outer-whitespace normalization. Complete PHP files masquerading as bodies are rejected. An empty body is legal and must correspond to an empty generated body. For bodies containing recognized placeholder/custom-code/Power tokens or `Text::` translation calls, both raw-source syntax and body comparison are explicitly deferred because generation may transform otherwise invalid PHP. The generated `code.php` still receives declaration and syntax checks.
- GUID existence for inheritance, interfaces, imports, forced loads, and embedded `Super___...___Power` tokens in source/settings. Missing GUIDs are reported together, with their originating Power.
- Catalogue hashes and structure; repeated catalogue identities are reported without collapsing their provenance.

This profile accepts preserved null/empty values where documented, unknown additional settings, list and keyed subform representations, and integer/string sentinels. It intentionally uses literal PHP identifiers for new class names. A historical definition with placeholders in the **name itself** requires target-context resolution outside this tool; do not replace a valid source placeholder merely to satisfy a static profile.

### Exact limits

Static success does not establish dependency type compatibility, inheritance cycles, imported aliases, service registration, Composer installation/autoload availability, full namespace/folder compilation, legal/licensing adequacy, runtime behaviour, or full transitive dependency closure. The validator uses membership in the local candidate index plus catalogue for reference existence; it does not emulate the consumer's final ordered resolution.

Tokenizer body/declaration checks establish only the consistency described above, not complete compiler equivalence: generated imports, inheritance clauses, licence headers and surrounding runtime setup need separate inspection. Recognized transformations are deferred and counted; unrecognized legitimate transformations may require source inspection rather than treating a failure as an implementation defect. Without PHP, body, declaration, namespace and syntax checks are all explicitly skipped. Inspect/rebuild generated representations through the supported compiler/export path.

Joomla Power tokens belong to a different catalogue format and are not resolved by this Super Power tool. JSON is parsed by `jq`; duplicate object keys are not comprehensively rejected, so reviewers must reject duplicate-key source JSON. These tools do not execute arbitrary source files, fetch external code placeholders, or install Composer packages.

## Schemas versus executable checks

The [index schema](../super-powers/schemas/index.schema.json) and [settings schema](../super-powers/schemas/settings.schema.json) are JSON Schema 2020-12 structural profiles for editors and external validators. They permit unknown settings to avoid deleting version-specific data. They are not official upstream JCB schemas.

The shell tools run purpose-built `jq` checks in `tools/jq`; they do **not** invoke a generic JSON Schema evaluator. Runtime checks additionally prove cross-file GUID/path/SPK consistency and apply the stated authoring policy. For example, a schema alone cannot compare a property's namespace suffix with a sibling name or establish that a selected GUID exists remotely. A schema pass is insufficient for acceptance. Keep both profiles aligned when the documented contract changes and add a focused regression case for the new rule.

## Check this documentation repository

```bash
bash tools/check.sh
shellcheck -x -P tools tools/*.sh tools/lib/*.sh tests/*.sh
```

`check.sh` checks shell syntax, parses all JSON, checks relative Markdown **file destinations** outside fenced code blocks, checks the Power and module registries, and runs `tests/run-tests.sh`. It does not validate remote URLs, Markdown fragments/anchors, full Markdown syntax, arbitrary reference-style links, or render diagrams. The CI workflow supplies PHP and ShellCheck and runs these checks on pull requests and pushes to `main`.

The tests use temporary synthetic catalogues and mutate the complete maintained [minimal repository](../super-powers/examples/minimal-repository/README.md). They exercise empty bodies, sentinels, malformed nested metadata, singleton JSON documents, identity/SPK/declaration/body drift, comment-only declaration spoofing, unsafe paths, incomplete/stale/tampered catalogues, unresolved references and ordered duplicates. Synthetic catalogue timestamps/mode labels are fixture inputs, not live-source evidence. Test files are cleaned automatically; no upstream repositories are changed.
